# Backup / restore / attachment lifecycle

## Storage
Local app data contains immutable data generations: `generations/<uuid>/clinic.db`, `files/<uuid>`, journals, and an atomically replaced current-generation pointer. Application resources in Program Files are read-only. No user-controlled relative filename is accepted by IPC. Original filenames are metadata only. Native selected files are validated against content signatures/size policy, assigned UUID internal names, streamed/hash-checked in background, flushed to staging, inserted in a transaction, then durably promoted with recovery journal. Symbolic links/reparse points outside managed roots are rejected. Upload limits default 100MiB per file, configurable owner policy; unsupported binaries rejected. Preview supported images/PDF in restricted viewer; other approved document formats open only after explicit native confirmation. A deletion tombstones DB metadata before cleanup; filesystem failure is reported/retried, never deletes another referenced file. Startup reconciles incomplete journal operations without discarding committed content.

## Archive format
Versioned `.dentivabackup` archive with `manifest.json`, SQLite snapshot, and referenced ready files. Manifest: format/app/schema version, clinic ID, installation lineage, UTC created time, actor ID, snapshot ID, each relative filename/size/SHA-256, database hash and total bytes. Use streaming archive with bounded entries/expanded size and reject absolute paths, traversal, duplicates, links, decompression bombs and unknown mandatory format fields. Include logo, staff photo, managed accounting attachments and all patient documents, not only patient photos. Never store passwords in manifest. Password hashes and records inside archive are encrypted with authenticated encryption; backup passphrase-derived key (Argon2id, per-archive salt), no hardcoded key. Recovery requires passphrase and owner credentials; print a safe local recovery procedure, not secret values.

## Consistent creation
Authorize privileged full-data backup; acquire mutation/attachment-publication gate; SQLite online backup API to staging snapshot (accounts for WAL); capture the referenced immutable-file manifest from that same snapshot; release write gate once file references are pinned. Stream copy/hash pinned files into archive; integrity_check + foreign_key_check snapshot; validate archive against manifest; flush then publish unique filename `DentivaPro_<clinic-id>_<YYYY-MM-DD_HH-mm-ss>_v<app>_s<schema>_<id>.dentivabackup`. Never overwrite existing archive. Success only after published archive verifies. Audit/backup record records completion after file publication; scheduler catches errors and emits notification. Retention is explicit and never deletes the last valid backup; no default auto-deletion.

Scheduler runs while app is open, intervals 7/15/30 days since last verified success; overdue job starts after authorized maintenance service initializes (not an interactive renderer session). Show due time, last success, destination/status/error. Windows-closed scheduling requires an explicitly installed scheduled task; do not falsely promise backups while application is not running. USB removal/read-only/no space returns actionable error, no fake success. Recommend at least one offline external copy.

## Restore state machine
1. Read any number of selected archives into a metadata catalog; filter by date/clinic/version; choose exactly one. No merge/concatenation of snapshots.
2. Reauthenticate authorized owner. Validate encryption, structure, all hashes, compatible schema, foreign keys, full DB integrity, clinic identity and all attachments in isolated staging.
3. Show counts, old/new clinic/time/schema and consequences. Exact typed clinic-name confirmation, explicit final confirmation.
4. Create AND VERIFY mandatory pre-restore backup of current generation; user-selected destination must be writable. Abort if it fails. Persist recovery intent outside the generation being replaced.
5. Enter exclusive maintenance state, reject new writes, revoke sessions, drain in-flight readers/writers, close database. Flush staged generation and restore journal.
6. Atomic pointer replacement to new generation on same volume. Validate again and perform approved migrations only on staged data. Persist committed phase.
7. Reopen, audit restore in restored DB and external protected recovery journal, notify and require login. Retain previous generation until safe cleanup and never before verified pre-backup.

Failure before commit leaves old pointer intact. Failure after pointer change rolls pointer back to old verified generation; on crash startup consults durable journal and checks both candidates, never guesses/deletes original. Power failure injection at every state boundary is mandatory. Backup/restored permission policies do not grant the currently logged-in actor authority in restored clinic: all sessions are invalidated.

## Local operations / reset
Database-open failure presents retry, restore through isolated recovery shell and sanitized diagnostics; no automatic replacement database. Activation reset is a documented Windows-local privileged action with owner reauthentication/recovery artifact and preserved audit; reinstall normally retains app data/receipt. Uninstall asks before removing user data, defaults preserve. Factory reset requires mandatory verified archive and typed clinic name; preserve external meta-audit. Restore copies cannot bypass activation on a new machine: receipt outside clinic backup.
